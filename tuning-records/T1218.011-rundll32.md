# Tuning Record: Suspicious Rundll32 Execution

**Platform:** Elastic Stack 9.2.4 (ES|QL over Sysmon Event ID 1), 3 Windows 11 lab hosts
**Technique:** T1218.011 System Binary Proxy Execution: Rundll32
**Date:** 2026-10-12

## Before
- Volume: 120 firings over 2026-10-11T00:00Z – 2026-10-12T20:00Z (hosts reported data in 17 of those hours)
- Hosts affected: 3
- Alerts per host: 40.0 (windows-lab 61, tuning-host2 34, tuning-host3 25)
- True positives: **2 of 2** executed atomics:
  - T1218.011 at 2026-10-12T19:11:45.830Z: `rundll32.exe shell32.dll,Control_RunDLL "C:\AtomicRedTeam\atomics\T1047\bin\calc.dll"`
  - T1218.011 at 19:13:46.647Z: `rundll32.exe url.dll,FileProtocolHandler calc.exe`
  - Not counted: T1218.011-2 at 19:09:44.628Z produced no payload process. Defender blocked its
    command line before the process started (`Trojan:Win32/Powessere.G`, confirmed in
    `evidence/defender-events.csv`).
- False positive rate: 118 of 120 = **98.3%**
- Top noise sources: about 15 distinct built-in Windows DLL/entry-point pairs, nearly all on all
  3 hosts, e.g.:
  - 17: `shell32.dll,SHCreateLocalServerRunDll {guid}` (parent powershell, SYSTEM)
  - 15: `/d acproxy.dll,PerformAutochkOperations` (Task Scheduler, SYSTEM)
  - 12: `inetcpl.cpl,ClearMyTracksByProcess 8` (parent powershell, SYSTEM)
  - 10 each: `Windows.StateRepositoryClient.dll,StateRepositoryDoMaintenanceTasks`,
    `CapabilityAccessManager.dll,CapabilityAccessManagerDoStoreMaintenance`
  - plus `Startupscan.dll,SusRunTask`, `sysmain.dll,PfSvWsSwapAssessmentTask`, `PcaSvc.dll`,
    `dfdts.dll`, `advapi32.dll,ProcessIdleTasks` and others

## Hypothesis
Written after grouping all 120 firings by parent, user and normalized arguments:
1. The noise is not a few known tools. It is the operating system itself, in about 15 shapes that
   will change with every Windows update. An exclusion list would be long, brittle and never
   finished.
2. The attacks are distinguishable by **how** rundll32 is used, not by the fact that it ran: a DLL
   from outside System32, or a built-in function that proxies execution of something else.

## Change
Technique: **narrow on behavior**. The rule flipped from allowlist-shaped
("alert on everything, excuse the good") to behavior-shaped ("alert only on abuse patterns"):
- **A.** any file path outside `C:\Windows\System32` / `SysWOW64` in the arguments (user folders,
  Temp, UNC/WebDAV, relative paths, or a DLL passed to `Control_RunDLL`). `C:\Windows\Temp` is
  deliberately not trusted because it is user-writable.
- **B.** known proxy-execution entry points (LOLBAS): `url.dll` FileProtocolHandler/OpenURL,
  `shell32` ShellExec_RunDLL, `advpack` LaunchINFSection/RegisterOCX, `setupapi`
  InstallHINFSection, `zipfldr` RouteTheCall, `pcwutl` LaunchApplication, `comsvcs` MiniDump
  (LSASS dumping), `mshtml` RunHTMLApplication, and others
- **C.** `javascript:` / `vbscript:` protocols, or an export called by ordinal (`,#N`)
- **D.** rundll32 with no arguments (a common process-injection host, e.g. Cobalt Strike spawnto)

**Before** (`detections/before/T1218.011-rundll32.esql`):

```sql
// LOOSE "BEFORE" RULE - deliberately naive. Do not deploy.
// Name:      Rundll32 Execution
// Technique: T1218.011 System Binary Proxy Execution: Rundll32
// Logic:     any rundll32.exe process at all
// Why naive: Windows itself runs rundll32 all day. This is the "alert on the LOLBin" rule.
FROM logs-windows.sysmon_operational-*
| WHERE event.code == "1"
    AND process.name == "rundll32.exe"
| KEEP @timestamp, host.name, user.name, process.parent.name, process.command_line
```

**After** (`detections/after/T1218.011-rundll32-suspicious.esql`):

```sql
// TUNED "AFTER" RULE
// Name:      Suspicious Rundll32 Execution
// Technique: T1218.011 System Binary Proxy Execution: Rundll32
// Before:    detections/before/T1218.011-rundll32.esql
//
// STRATEGY FLIPPED: allowlist -> behavior.
//   The before rule alerted on ANY rundll32. Our data showed ~15 distinct built-in Windows
//   DLL/entry-point pairs, run by Task Scheduler on every host. Excluding them one by one would
//   need 15+ exclusions that break on the next Windows update. Instead, alert only when rundll32
//   shows a behavior attackers rely on:
//   A. A file path outside C:\Windows\System32 / SysWOW64 anywhere in the arguments
//      (DLL in Temp, Public, Downloads, a UNC/WebDAV share, or passed to Control_RunDLL).
//      Note: C:\Windows\Temp is deliberately NOT trusted - it is user-writable.
//   B. A known proxy-execution entry point: a built-in function that launches other programs,
//      installs INF files, runs script, or dumps process memory (comsvcs MiniDump = LSASS dump).
//   C. Script protocols (javascript:, vbscript:) or a DLL export called by ordinal (,#N).
//   D. No arguments at all - an empty rundll32 is a common process-injection host.
//   Matches on PE OriginalFileName too, so a renamed rundll32 is still caught.
//
// GOTCHA: "#" is reserved in Elasticsearch (Lucene) regex - it matches nothing. Escape it as \#.
//   The first draft of check C used a bare "#" and silently never matched; a unit test caught it.
//
// TRADE-OFF: this is a denylist of techniques. A NEW abuse of a System32 DLL that is not in list B
//   will be missed. Revisit list B when new LOLBAS entries for rundll32 are published
//   (lolbas-project.github.io), and pair with a low-severity "rare rundll32 DLL,entrypoint"
//   prevalence hunt to catch what B does not name.
FROM logs-windows.sysmon_operational-*
| WHERE event.code == "1"
    AND (process.name == "rundll32.exe" OR process.pe.original_file_name == "RUNDLL32.EXE")
| EVAL cl = TO_LOWER(process.command_line)
// A: remove trusted system paths (including rundll32's own path), then look for any path left
| EVAL non_system = REPLACE(cl, """c:\\windows\\(system32|syswow64)\\""", "")
| EVAL a_path = non_system RLIKE """.*([a-z]:\\|\\\\|\.\.?\\).*""",
       b_entry = cl LIKE "*url.dll*fileprotocolhandler*" OR cl LIKE "*url.dll*openurl*"
              OR cl LIKE "*shell32*shellexec_rundll*" OR cl LIKE "*advpack*launchinfsection*"
              OR cl LIKE "*advpack*registerocx*" OR cl LIKE "*setupapi*installhinfsection*"
              OR cl LIKE "*syssetup*setupinfobjectinstallaction*" OR cl LIKE "*zipfldr*routethecall*"
              OR cl LIKE "*pcwutl*launchapplication*" OR cl LIKE "*comsvcs*minidump*"
              OR cl LIKE "*mshtml*runhtmlapplication*" OR cl LIKE "*desk.cpl*installscreensaver*",
       c_script = cl LIKE "*javascript:*" OR cl LIKE "*vbscript:*" OR cl RLIKE """.*,\#[0-9]+.*""",
       d_empty = cl RLIKE """.?(c:\\windows\\(system32|syswow64)\\)?rundll32(\.exe)?.? *"""
| WHERE COALESCE(a_path OR b_entry OR c_script OR d_empty, false)
| KEEP @timestamp, host.name, user.name, process.parent.name, process.command_line
```

Why this technique over the alternatives:
- **Exclusions (technique 5)** would need 15+ entries, each a maintenance item that breaks on the
  next patch, and each a potential hiding place.
- **Prevalence baselining (technique 3)** fits on paper, since the noise is high-prevalence and the
  attacks were on one host. But with 3 hosts, "common" means 2 or 3 machines, so an attacker who
  touches two hosts becomes "normal". Better kept as a separate low-severity hunt than baked into
  the rule (see below).

## What this gives up
- **It is a denylist of techniques.** A new abuse of a legitimate System32 DLL that is not in
  list B, and that loads nothing from outside System32, is missed. The old rule (any rundll32)
  would have fired on it, buried among 118 others. Mitigation: re-check list B against new LOLBAS
  rundll32 entries (lolbas-project.github.io) at each review, and run a "rare rundll32
  DLL,entrypoint pair" prevalence hunt to surface what B does not name.
- **Bare DLL names are trusted.** `rundll32 foo.dll,Bar` with no path resolves from System32 first,
  but DLL search-order tricks (a planted DLL in the working directory, when it does not exist in
  System32) are not covered unless they also hit A–D.
- Gains: renamed rundll32 is caught (matches `OriginalFileName`), and techniques the old rule saw
  but no analyst would find among 120 alerts now stand alone.

## Validation
- All 2 atomic executions still detected: **yes**
- Volume delta: 120 → 2 (**98.3% reduction**). Both remaining firings are the atomics.
- Unit tests: 15 synthetic command lines (10 malicious covering every branch A–D, 5 real benign
  lines from this environment) run through the exact rule logic with ES|QL `ROW`
  ([`tests/test_rundll32.py`](../tests/test_rundll32.py)).
  **First run: 14/15. The ordinal case `evil.dll,#1` did not fire.** Cause: `#` is a reserved
  character in Elasticsearch's (Lucene) regex syntax and matches nothing, so branch C could never
  match an ordinal. Fixed by escaping (`\#`); second run 15/15. None of the real atomics used an
  ordinal, so without the synthetic tests this would have shipped as a silent gap.
- Anything that stopped firing which should not have: none known. Everything that stopped firing
  was a built-in DLL called from System32 with a non-proxy entry point.
- **Caveat:** tuned and validated on the same data window. No held-out window yet.
